# Robot harness 与验收

[English](harness.md) · [README](../README.zh-CN.md)

设计借鉴 [Code as Policies](https://code-as-policies.github.io/) 的能力组合思路，采用“观测 → 有限操作 → 检查证据 → 保存结果”的闭环。当前没有执行语言模型生成策略，也不需要模型 API；实际控制由确定性程序和 Nav2 负责。

`harness/client.py` 提供 `observe`、`stop`、`start_recording`、`next_instance`、`end_recording`、`start_mapping` 和有限时长的 `drive_for`。默认禁止移动；只有显式设置 `allow_motion=True` 才能调用移动能力，而且仍需通过车端全部检查。`Outcome.verified` 只验证该操作声明的后置条件：限时驾驶验证的是最后已经停车，不代表测得的行驶距离符合目标。

```python
from harness.client import LimoHarness
robot = LimoHarness()  # 默认禁用移动
state = robot.observe()
assert robot.stop().verified  # 不结束录制
```

静止诊断不会启用驾驶：

```sh
.venv/bin/python -m harness.diagnose --seconds 60 --output /private/check.json
```

报告分开检查里程计位移、地图位姿漂移、地图可用性和录制状态；不会把路线／探索标成已经通过。`harness.replay` 本地读取校验后的文件并导出指标，`harness.recover` 在保留原件的前提下恢复完整且 CRC 正确的记录，两者不包含 ROS 发布或网络操作。

## 验收标准

| 项目 | 所需证据 |
| --- | --- |
| 录制生命周期 | 连接不录制；停车后会话和数据继续；显式结束才正常完成 |
| 连续分割 20 次 | 收到的传感器序号、视频时间戳无重复且正确分段；普通分段不请求停车 |
| 持续录制 | 所选规格运行 30 分钟；无无法解释的样本／帧序号缺口，计数与归档一致 |
| 无损视频 | 解码 FFV1／PNG，与源 RGB 像素哈希比较 |
| 传输故障 | 损坏、截断、ACK 中断不删除未校验副本，重试幂等 |
| 存储／断线 | 驾驶锁定、异常可见、原件保留，不自动重新启用驾驶 |
| 静止 SLAM | 60 秒，里程计位移 <2 cm，地图定位漂移 <5 cm、<2° |
| 动态 SLAM | 独立测量的 2 米直线、90° 转弯和闭环；终点误差 ≤15 cm／5°，检查墙体一致性 |
| 自动建图 | 三次探索，每次到达至少三个可达边界；面积有增长，无盲走兜底，能按限制停车 |
| 保存／重载 | 栅格和 SLAM 状态完整，按实际位姿重载后核对定位与障碍物 |

不接硬件的测试不能证明动态项目合格。只有做过对应测试，才公布聚合结果；真实 MCAP、视频、地图和详细报告留在公开仓库之外。不能仅凭 `/map` 新鲜或 HTTP 200 宣称成功。

## 已知限制

- 录制器接收之前的 DDS 丢包，不能靠接收序号补回或证明不存在。
- 测试驱动提供角速度，没有实际转向角和轮编码器话题。
- 摄像头、网络和磁盘吞吐取决于规格和系统负载。缓冲溢出需要记为异常，不能悄悄压缩时间线掩盖缺口。
- 桌下或靠墙位置可能没有满足车身净空的探索边界。此时会说明原因并停车，不会为了增长地图而驶入未知区域。
- 崩溃恢复后的尾部不完整；摄像头或机器人重启后，可能需要用户明确开启新会话以重建时钟和序号关系。
